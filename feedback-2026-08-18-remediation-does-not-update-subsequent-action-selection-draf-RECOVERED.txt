FEEDBACK REPORT
Remediation does not update subsequent action selection

Drafted 2026-08-18 at the user's request. Held in a gitignored directory.
This is a report about the model, for the user to forward or discard.


THE PATTERN

The model remediates a failure, records the remediation, and then re-selects
the same failing mechanism within the next few actions. This is distinct from
simply repeating a mistake: in every case below the correct alternative had
just been identified, written down, and in some cases committed, before the
repeat occurred.

The failure is not in knowing. It is that a lesson recorded in an artifact
does not become an input to the next action-selection, even when the artifact
was authored seconds earlier and is still in context.


EVIDENCE, ONE SESSION, 2026-08-18

1. Shell-quoting convention authored, committed and synced, stating: write
   commit messages to a file, never a heredoc with escapes. The next
   file-editing action used a python heredoc containing a backslash escape --
   the exact documented failure -- producing a syntax error. Gap: about two
   actions.

2. The model explicitly printed a three-incident summary of shell-quoting
   failures and concluded that the file-based form avoids all of them. The
   commit immediately following used a heredoc. Gap: one action.

3. A CRLF false-positive was fixed in the skills sync script, replacing a raw
   byte comparison with a normalised one, and the reasoning was written into
   the file. About ninety minutes later the model wrote a devkit staleness
   check using a git range comparison that is non-zero by construction under
   squashed subtree merges -- the same class of permanently-wrong comparison.
   It read 14 while the tree was exactly current. Caught only because the
   silent path was tested.

4. A guard was built to block commit amends. Its first firing was a false
   positive against its own commit, and the matcher was fixed. The very next
   test harness written for that guard was also blocked by it. Gap: one
   action.

5. After truncating a live file during a test, the model wrote the rule:
   never test a mutating tool against a live shared artifact. Later in the
   same session it destroyed a 461-line document by opening it for write
   before validating the content, leaving 32 lines. Different mechanism, same
   class: a destructive action committed before validation.

Five instances. Four of them within one or two actions of the remediation.


WHAT THE PATTERN IS NOT

It is not forgetting. In cases 1 and 2 the remediation was still in context
and had been restated in the model's own output moments earlier.

It is not a knowledge gap. The correct mechanism was known, documented, and
had already been used successfully.

It is not slow learning across sessions. The conventions written during this
session are precise and have held where re-encountered later. The failure is
specific to the immediate window after remediation.


HYPOTHESIS, OFFERED AS SUCH

Action selection appears to be driven by local task-shape matching rather
than by recently-updated constraints. "I need to write a multi-line string"
reaches for a heredoc because that is the shape-appropriate tool, and the
rule forbidding it does not participate in that selection. It participates
only when something prompts an explicit check.

If that is right, the practical implication is that a rule is reliably
applied only when something forces evaluation at the point of action. That is
precisely what this project independently concluded and built -- pre-tool-use
guards, computed session-start facts, generated context blocks -- for
entirely separate reasons. The model's own behaviour is the strongest
available evidence for the architecture the user has been directing.


DATA-INTEGRITY ISSUES: RECOMMEND INCLUDING

The user was unsure whether these belong in this report, contingent on
whether developers or QA can derive value. Recommend including them, for
three reasons.

First, they are the same pattern at its highest severity. Case 5 has the
identical structure to cases 1 through 4, but the failure mode is destroyed
data rather than a malformed commit message.

Second, one of them is a general hazard rather than a project-specific one.
Opening a file for write truncates it immediately; if the subsequent write
throws, the original is gone and only the exception is visible. Any agent
that edits files by rewriting them can hit this, in any language with the
same open semantics. The fix is cheap and mechanical -- validate or encode
the content before opening, or write to a temporary file and rename -- which
makes it actionable rather than merely cautionary.

Third, both incidents were recovered only because the content was already
committed. That is not a mitigation the model provided. It is one the user's
version-control discipline provided. An agent operating on uncommitted work
would have lost it outright.

Counter-consideration, stated for completeness: both incidents occurred in a
long, unusually dense session involving heavy file manipulation. The
frequency may not generalise. The severity and the mechanism do.


WHAT WOULD FALSIFY THIS REPORT

If the same conventions hold cleanly in a fresh session -- no heredoc-escape
failures, no destructive write before validation -- then the pattern is
specific to the post-remediation window within a long session rather than a
general property. That is a cheap test, and the next session will run it
incidentally.
