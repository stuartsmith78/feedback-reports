FEEDBACK REPORT

Subject: A Claude Code session cannot learn the address by which every other
session addresses it

Date: 2026-08-22
Reporter: Claude Opus 5, at the user's request


Claude Code sessions on one machine can message each other by a short name,
and the tool's documentation states that the name is the address. Every session
can see every other session's name. No session can see its own.

Three surfaces were checked by name before this was written. The agent listing
returns peer rows and omits the caller. The session-metadata lookup explicitly
refuses the current session. A separate presence registry holds self-assigned
slugs in a different namespace with no mapping to the messaging address. The
names also rotate, four or more times across three sessions in one working day.

Eleven observations, three independent sessions, one day.

The negative case is established rather than asserted, and it is the reason we
are sending this. One session had written a durable note that same day
recording that a session cannot see its own address. Hours later, asked to
introduce itself, it inferred an address from a peer listing that by definition
could not contain it, and misrouted a long technical briefing to a different
project's session. The knowledge was present and recently written; the action
still went the other way. Its own diagnosis: the alternative to guessing is to
ask a peer and wait, and nothing signals that guessing is unsafe. A listing
that returns four confident rows and silently omits a fifth reads as a listing,
not as incomplete.

Rotation compounds it in a counter-intuitive direction. A longer message takes
longer to compose and is likelier to be sent to an address that has since
rotated, so short exchanges succeed and substantive ones fail. Re-listing
before every send is already the prescribed sequence and narrows the window
without closing it. The bounce does suggest a near-miss name, but paired
measurement shows the suggestion works when old and new names share a stem and
produces nothing when they differ, which is the case that needs it. Twice, a
bounce was read as the recipient having ended while both sessions were live.

The information is published to every party except the one it identifies, so
this is not an isolation boundary. Recommended fix: return a self row in the
listing, marked as the caller.
